# 0001. 查询拆成 surface / relation / intention 三类原子条件

- 状态：接受
- 日期：2026-07-09（决策发生时间，见 [CHANGELOG](../../CHANGELOG.md)；本文档 2026-07-30 补写）

## 背景

Agent 做代码检索时，一条自然语言查询里往往同时压着三种完全不同性质的要求。
比如「找处理用户登录鉴权的入口函数，不要测试代码」里就有：

- 字面线索：`login`、`auth` 这些词大概会出现在符号名里；
- 结构约束：它得是个「入口」，即在调用图里是被外部调用的那一端；
- 语义要求：「处理鉴权」是功能描述，符号名里不一定有这些词。

已有的两种做法各自只能吃下其中一部分（详见 [semql-report.md](../semql-report.md)）：

| 方案 | 问题 |
|---|---|
| Grep / 词法检索 | 处理不了语义等价的不同命名，召回受限于字面形式 |
| Dense Vector Search | 表达不了精确约束，输出是连续相似度，难以组合和解释 |
| 两者叠加 | 管道彼此孤立，无法表达条件之间的逻辑关系，执行顺序也没法优化 |

更根本的问题是：这两种范式都把代码检索建模成**一维相似度排序**，
而 Agent 实际需要的是**带约束的多维匹配**——本质上更接近数据库查询，
而不是搜索引擎排序。

## 决策

把一条查询拆成三类**原子条件**（SemCon），各自编译成独立的执行计划，
再按代价从低到高串起来执行：

| 条件类型 | 匹配什么 | 靠什么执行 | 代价 |
|---|---|---|---|
| **Surface** | 字面/词法：符号名、关键词、代码片段 | 倒排索引、ngram、缩写扩展 | 最低 |
| **Relation** | 结构：caller/callee、图角色、文件路径 | 代码图库、LSP、CodeQL | 中 |
| **Intention** | 语义：功能职责、业务意图 | 聚类、embedding、LLM 判定 | 最高 |

每条条件带一个 `property` 字段标记 `include` 或 `exclude`。

三者各有一个 planner，**只解析自己那类字段**，产出三份独立的 JSON 计划；
executor 只读计划，不碰原始 SemCon。契约见
[ARCHITECTURE.md](../../ARCHITECTURE.md#planner-与-executor-的契约)。

## 被否决的方案

### A. 单一条件类型 + 一个打分函数

把所有线索揉成一个加权打分：`score = α·词法 + β·结构 + γ·语义`。

看着可行：实现最简单，只需要一个排序，调三个权重就能试各种配置。

没选的原因：

1. **表达不了硬约束。** 「不要测试代码」是个布尔条件，不是「测试代码扣 0.3 分」。
   加权打分只能压低它的排名，压不掉它。
2. **没法解释。** 结果只有一个总分，Agent 拿到之后没法知道这条为什么被选中，
   也就没法基于它继续推理。
3. **权重不可迁移。** 一组在 Java 项目上调好的 α/β/γ，换个项目就得重调。

### B. 只拆两类：词法 vs 语义

把 relation 归进 surface（都算「精确匹配」）或归进 intention（都算「需要理解」）。

看着可行：两类比三类简单，而且结构约束确实既有精确的一面也有推理的一面。

没选的原因是**执行代价差了两个数量级**。词法匹配走内存倒排索引是微秒级，
结构约束要查图库或起 LSP 是毫秒到秒级，语义判定要调 LLM 是秒级。
把它们合并意味着无法按代价排序执行，也就丢掉了「先用便宜的条件把候选集砍小、
再用贵的条件精排」这个最重要的优化手段。

### C. 直接让 LLM 输出一段可执行 DSL

跳过条件抽取，让 LLM 一步生成完整的查询表达式。

看着可行：少一层中间表示，LLM 也确实能写出结构化输出。

没选的原因：LLM 同时负责「理解意图」和「安排执行」时，两件事都做不好——
它不知道当前项目里哪些索引存在、哪个条件选择性更高。把这两件事分开之后，
LLM 只负责它擅长的语义抽取，执行顺序交给 planner 按规则和代价决定。

## 代价

1. **多了一层中间表示。** SemCon → SemQL → 执行计划，链路变长，调试要多看一层产物。
   代价是实打实的，缓解手段是每个阶段都把中间结果落盘（`semCon.json`、
   `*_semql.json`），出问题能逐层对。
2. **条件之间的交互没有被建模。** 三类条件目前是串行执行、逐层过滤的，
   一个候选被 surface 阶段砍掉之后，intention 阶段再有多确信也救不回来。
   `filters/cluster_pipeline.py` 里的 rescue 机制算是个补丁，不是根本解法。
3. **分类本身有灰色地带。** 「找 Controller 类」到底是 surface（名字里有 Controller）
   还是 relation（在架构上处于入口层）？目前靠 LLM 抽取时自行判断，
   不同 query 上不完全一致。

### 什么时候该重新考虑

如果发现大量查询的效果瓶颈在于「条件之间需要互相参考才能判断」，
而不是「单类条件本身不够准」，那说明串行过滤这个模型到头了，
该考虑联合打分或者迭代式执行。
