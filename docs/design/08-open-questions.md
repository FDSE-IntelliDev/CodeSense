## 挡住实现的

> 片段统一（[03](03-data-model.md)）本身也是个赌注：更保守的做法是
> ElementSet / PathSet 两套类型。判断依据是真实查询里「只要一个元素列表」
> 的场景占比——`only_nodes()` 如果到处都在调，说明该退回两套类型。
> **需要用真实查询验证**，这也是下面「一个能跑通的最小 QL」要回答的问题之一。

### Q1. `hop` 的路径爆炸怎么控

三跳、几百个起点，路径数轻松上百万。已知手段：`max_paths` 截断、
双向 BFS、按路径长度剪枝。但**截断意味着结果不完整且不确定**——
同样的查询跑两次可能返回不同的路径子集。

选项：

- **A** 截断但保证确定性（按 symbol_id 排序后取前 N）。可复现，但截掉的
  可能恰好是好结果。
- **B** 不返回全部路径，只返回**端点对 + 一条代表路径**。内存可控，
  但丢掉了「有几条路径连着」这个强信号。
- **C** 惰性求值，`endpoints` 只要端点时不物化路径。实现复杂。

倾向 A + B 组合：默认只留代表路径，需要全部时显式打开。**需要定。**

### Q2. 单元之间的默认关系是 AND 吗

`io performance on disk` 里三个单元，脚本写的是 `io & disk` 然后
`hop(..., perf)`。但这个编排是手写的，编译器凭什么这么排？

- 两两之间可能是：同元素共现（`&`）、图上可达（`hop`）、
  或者根本无关（只是描述同一件事的不同侧面）。
- 组合数随单元数增长很快。

[06](06-script-and-execution.md) 的编译回路解决了一半——**不必一开始就猜对，
试跑会告诉你**：`io & disk` 只剩 3 个就放宽，剩几百个就收紧。

剩下的一半是**初始猜测**：从哪个编排起步？全 `&` 起步在泛词查询上大概率
直接归零，全 `hop` 起步又太贵。倾向按单元的「具体程度」定：
具体的单元（`disk`）之间用 `&`，抽象的单元（`performance`）用 `hop` 挂上去。
**没验证过。**

### Q3. 生成脚本的安全边界

[06](06-script-and-execution.md) 列了三条（受限命名空间、AST 白名单、人工确认），
但没定死。核心问题：**白名单允许到什么程度？**

- 只允许算子调用 + 集合运算 + 赋值 → 最安全，但可能表达不了某些查询
- 允许 `if` / `for` → 表达力强，但白名单校验形同虚设

倾向从最窄开始，遇到表达不了的再放宽——**而且每次放宽都应该先问
「是不是缺算子」**。需要真实查询样本来验证窄白名单够不够用。

## 影响设计但不挡实现的

### Q4a. 多信号怎么合成

[04](04-query-unit.md) 给了三个选项（`max` / `sum` / `noisy_or`），默认 `noisy_or`。
但各 satisfier 的权重是拍脑袋定的（`annotation` 0.9、`lexical` 0.5），
而且它们**未必独立**——`@Cacheable` 标注的方法名字里往往也有 `cache`，
`noisy_or` 会重复计一次。

需要真实数据来标定。在有评测集之前，怎么定都是猜。

### Q4b. `derived` 词的权重怎么定

[04](04-query-unit.md) 给 `buffer` 打了 0.5，但那是拍脑袋。合理的做法：

- 让 LLM 给（一致性差）
- 按项目语料的共现强度算（需要索引，编译不再纯粹）
- 固定按 source 分档：literal 1.0 / synonym 0.8 / derived 0.5（简单，但一刀切）

**倾向先用固定分档，等有评测数据了再调。** 现在没有评测集，
调也是瞎调。

### Q5. 数据流边怎么抽

设计里 `flows_to` / `reads` / `writes` 已经是一等边类型（[03](03-data-model.md)），
不再是「将来再说」——「这个参数的值从哪来」是理解代码时最常问的问题之一。

未定的是**怎么抽**：

- CodeQL：现成的数据流分析，但要为每个项目建库，重且慢
- LSP：能拿到引用，但 def-use 链要自己接
- 轻量 AST：只做函数内数据流，跨函数靠 `calls` 边近似

倾向**先做函数内 + 跨函数近似**，够用再上 CodeQL。
但「近似」的误差有多大没量过，`Edge.confidence` 该给多少也不知道。

### Q6. `co_change` 算子值不值得

「在 git 历史里总是一起改的文件」是很强的信号——
整理这个仓库时，用共现分析找出过真实的抽象泄漏（schema 和它的消费者
每次都一起改）。

但它和代码结构是**正交**的信息源，混进 QL 会让语义变复杂：
`hop(a, b, edge="co_change")` 里的「边」根本不是代码里的边。

**倾向单独做成一个分析工具，不进 QL。**

### Q7. 边缺失时怎么降级

不同语言、不同项目能抽到的边类型不同：Java 能拿到注解和实现关系，
C 项目没有注解；数据流可能只在部分语言上有。

`hop(edge="flows_to")` 在没有数据流边的项目上该怎么办？

- 返回空 —— 诚实，但用户会以为「没有这样的代码」
- 跳过该约束 —— 结果不可信，且用户不知道
- **报错并说明缺什么** —— 倾向这个，但要让编译器能提前知道索引有哪些边，
  从而在编译期就避开不可用的算子

也就是说**索引应该声明自己的能力**（有哪些边、覆盖哪些语言），
编译器读这份声明来编排。这一条影响接口设计，**优先级不低**。

## 需要先有的东西

### 评测集

[07](07-mapping-to-current.md) 的迁移路径要求「每阶段能回答比老的好在哪」，
但现在**没有评测集**——`evaluation/` 是空骨架，`data/` 里只有几条样例 query。

没有评测，所有关于召回和精度的判断都是猜的。这是**优先级最高的前置工作**，
比实现任何算子都靠前。

至少需要：

- 20–50 条真实查询，覆盖不同类型（词法为主 / 图为主 / 语义为主）
- 每条查询的人工标注答案集
- 一套指标（代码检索一般用 MRR / Recall@k / nDCG@k）

### 一个能跑通的最小 QL

在动编译器之前，先手写 3–5 段 QL 脚本覆盖不同查询类型，
验证**算子集合够不够用**。写不出来的地方就是缺的算子。

这一步很便宜（几百行），但能避免把编译器建在错的算子集上。
