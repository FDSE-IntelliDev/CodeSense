# 设计文档

CodeSense 下一版的设计：**把一条自然语言查询编译成一段针对代码库的查询脚本**，
脚本本身是若干基本查询算子的编排。

> **状态：初稿，未实现。** 这里描述的是目标形态，不是当前代码。
> 当前实现是固定三段管线（surface → relation → intention），
> 对应关系与迁移路径见 [07](07-mapping-to-current.md)。

## 一句话

```
自然语言 query  ──编译──>  QL 脚本（Python）  ──执行──>  带证据的结果
```

编译产物是**可读、可改、可单步跑**的一段代码，而不是一份 JSON 计划。

## 四个核心判断

**1. 查询是算子编排，不是固定管线。**
现在 surface → relation → intention 的顺序是写死的。但「先按调用图圈定范围、
再在范围内做词法匹配」这种更省算力的顺序，现有结构表达不出来。

**2. Query unit 是语义槽位，不是关键词袋。**
`io performance on disk` 拆成三个单元，每个单元**可由多种信号满足**——
词法、注解、结构位置、修饰符、语义相似度。不把词拼成一条大 regex，
因为图约束和意图判断是**挂在单元上**的：「performance 相关的代码调用了
disk 相关的代码」——这句话里两个单元落在不同元素上，靠图连起来。

**3. 答案是代码片段，不是元素列表。**
`BlockDevice.write → AsyncWriter.submit → BatchPool.acquire` 这三个节点加两条边
才是答案；拍成一个列表就丢掉了使它成为答案的结构。所以核心数据类型是
**带证据的子图**，所有算子都是 `Frag -> Frag`。

**4. 编译产物是代码，而且编译是个回路。**
JSON 计划只能被解释器执行，出了问题只能看日志；Python 脚本可以打断点、
注释一行看差异、手工改完再跑。而且编排的好坏在跑之前判断不了——
`io & disk` 剩几个候选取决于项目的命名习惯，所以编译该是
「拟一版 → 试跑 → 修正」的回路。

## 与 SemQL 的关系

这不是推翻 SemQL，是把它的执行层从「解释固定 schema」换成「编排算子」。
SemCon 抽取（NL → 三类原子条件）这一步保留，
它产出的东西从「三份 plan JSON」变成「一段 QL 脚本」。

三类条件与算子的对应：

| SemCon 条件 | 对应算子 |
|---|---|
| Surface（字面匹配） | `lexical` satisfier —— 但它只是单元的**多种信号之一** |
| Relation（结构约束） | `hop` / `contains` / `degree` |
| Intention（语义要求） | `intent` / `semantic` satisfier |

原先「三类条件串行过滤」的隐含假设——每类条件独立地筛同一个候选集——
在新模型里不再成立：它们是同一段脚本里可以任意组合的算子。

更进一步的解绑是：**一个查询单元可以被词法、注解、结构位置、修饰符、
语义相似度等多种信号满足**，词法不再是唯一入口。`@Async` 标注的方法
名字里可能一个性能词都没有——纯词法必然漏。

单元需要的那批词**不由 LLM 现场生成**——那会把大模型放在每条查询的
关键路径上。它们来自离线建好的扩展表：全局预训练 + 本项目微调的词向量
给语义邻近，lexical rules 给缩写变体，两者取合取。见 [09](09-grounding.md)。
