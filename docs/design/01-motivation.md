# 01 动机：为什么放弃固定三段管线

## 现在是什么样

一条查询被拆成三类原子条件（SemCon），编译成三份计划，由三个 executor
按固定顺序串行执行：

```
候选全集
   │
   ├─ SurfaceExecutor    倒排索引 + 缩写扩展，按关键词收窄
   ├─ RelationExecutor   调用图 / caller / callee / 图角色，继续收窄
   └─ IntentionExecutor  聚类 → embedding → LLM judge，再收窄
   │
最终结果
```

这套结构解决了真问题——为什么要把查询拆成三类、为什么按代价从低到高排，
理由见 [ADR 0001](../decisions/0001-semcon-three-condition-split.md)，那些判断至今成立。

下面说的是它**表达不了**的东西。

---

## 问题 1：执行顺序写死了

三段的顺序是代码结构决定的，不是查询决定的。但对不同的查询，最优顺序不同：

- **`Find the entry function that handles user login`**
  先词法（login/auth 关键词很有区分度），再图（entry_point 角色）。当前顺序恰好合适。

- **`哪些函数被 TokenManager.refresh 调用`**
  图约束本身就把候选压到个位数，先跑图再做别的最省。当前实现会先跑一遍
  全量词法匹配——而这个查询根本没有有意义的关键词。

- **`io performance on disk`**
  三个词都很泛，词法匹配会返回大量噪音；真正有区分度的是
  「这些元素之间有没有调用关系」。当前结构里，图只能用来**过滤**
  词法结果，不能用来**产生**候选。

顺序写死的代价不只是慢，是**有些查询根本表达不出来**。

## 问题 2：串行过滤会丢结果，而且救不回来

三段是逐层收窄。一个候选被 surface 砍掉，后面 intention 再确信也没机会。

`filters/cluster_pipeline.py` 里的 rescue 机制就是在打这个补丁——
把被聚类判为低相关的候选捞回来，交给下一层再看一眼。补丁能缓解症状，
但改不了「信息只能单向流失」这个结构。

根因是：**三类条件被假设为独立地作用在同一个候选集上**。而真实查询里
它们常常互相定义——「和鉴权相关的（intent）那个入口函数（graph role）」
里，intent 判断的对象应该是图筛过之后的小集合，而不是全量候选。

## 问题 3：关键词被拍平成一个袋子

当前 SurfacePlan 里已经有 `keyword_groups` 的结构（组内 OR、组间 AND），
这个方向是对的。但组只是**匹配时**的分组，一旦匹配完成，组的身份就消失了——
后续的 relation 和 intention 条件挂在整个候选集上，不挂在具体的组上。

于是这句话表达不出来：

> **performance 相关的代码** 调用了 **disk 相关的代码**

这里有两个关键词组，各自匹配到**不同的元素**，靠调用边连起来。
它不是「同时含有 performance 和 disk 关键词的元素」——那样的元素几乎不存在。

> 有意思的是，当前实现里其实已经埋了这个能力的雏形：
> `SurfaceGroupLogic(groups, graph_scope, hop_count)` 允许在 keyword group
> 之间声明图约束。但它是 surface 执行内部的一条组合规则，
> 产出仍然是一个扁平的元素集——**路径信息在返回前就被丢掉了**。

## 问题 4：关键词只从 query 里抠，不做语义派生

`io performance on disk` 这条查询，字面上只有三个词。但一个有经验的人会去搜：

- performance → `buffer`、`async`、`cache`、`batch`、`pool`
- disk → `swap`、`block`、`sector`、`flush`、`sync`

这些词**不是同义词**——`buffer` 不是 `performance` 的同义词，它是
「代码在处理性能问题时通常会出现的东西」。当前的同义词扩展
（`terms[].source: keyword | synonym`）覆盖不了这一类。

---

## 所以要改成什么

把执行层从「解释固定 schema 的三个 executor」换成「**若干基本算子 + 一段编排它们的脚本**」：

| 当前 | 目标 |
|---|---|
| 顺序写死在代码里 | 顺序由编译出来的脚本决定，每条查询可以不同 |
| 三段逐层收窄，信息单向流失 | 算子自由组合，图可以产生候选而不只是过滤 |
| 关键词组只在匹配时有意义 | Query unit 是一等公民，图约束和意图判断都挂在单元上 |
| 关键词 = 查询里的词 + 同义词 | 关键词 = 单元语义的**派生**，区分同义与联想 |
| 产物是三份 JSON 计划 | 产物是一段可读可改可单步跑的 Python 脚本 |

**不变的部分**：SemCon 抽取（NL → 结构化条件）、按代价从低到高的直觉、
证据要贯穿全程。这三条在 ADR 0001 里论证过，新设计继承它们。
