# 06 脚本形态与执行

## 为什么产物是脚本，不是 JSON 计划

当前编译产物是三份 JSON（`surface_semql.json` / `relation_semql.json` /
`intention_semql.json`），由三个 executor 解释执行。改成一段 Python 脚本的理由：

| | JSON 计划 | Python 脚本 |
|---|---|---|
| 出问题怎么查 | 读日志，猜解释器怎么走的 | 打断点、注释一行看差异 |
| 改一下再试 | 改 JSON，还得懂 schema | 改代码 |
| 表达组合 | 受限于 schema 预设的算子和顺序 | 任意表达式、变量、注释 |
| 复现 | 要连同解释器版本一起存 | 脚本本身就是完整描述 |
| 新增算子 | 改 schema + 改解释器 | 加一个函数 |

研究场景里「改一下再试」发生得极其频繁，这一条基本决定了选择。

**代价**：脚本是可执行代码。如果 LLM 生成的脚本直接跑，就等于执行模型产出的
代码。缓解手段见下面「安全」一节。

## 脚本长什么样

```python
"""io performance on disk

编译自：io performance on disk
生成时间：<stamp>    索引版本：<commit>
"""
from codesense.ql import Query, annotation, hop, intent, lexical, of_kind, structural

q = Query("io performance on disk")

# ── query units ──────────────────────────────────────────────
io = q.unit("io", concept="和输入输出有关的代码", satisfiers=[
    lexical(["io", "input", "output", "read", "write", "stream", "flush"]),
])
disk = q.unit("disk", concept="和磁盘存储有关的代码", satisfiers=[
    lexical(["disk", "swap", "block", "sector", "volume", "storage"]),
    structural(package=r".*\.(storage|fs|vfs)\..*", weight=0.7),
])
perf = q.unit("performance", concept="代码在优化或影响性能表现", satisfiers=[
    lexical(["buffer", "async", "cache", "batch", "pool", "latency"], weight=0.5),
    annotation(r"@(Async|Cacheable)", weight=0.9),
])

# ── 编排 ─────────────────────────────────────────────────────
# 磁盘 IO 的落点：同时沾 io 和 disk 的可调用元素
disk_io = of_kind(io & disk, "function", "method")

# 从落点出发，三跳内够到 performance；调用或数据流都算
f = hop(disk_io, perf, edge=["calls", "flows_to"], len=(1, 3), avoid=q.tests)

# 只对路径起点做语义判定 —— intent 最贵，放最后、作用在最小片段上
answer = intent(f.roots(), perf.concept)

q.emit(answer, context=f)
```

几个刻意的选择：

- **每个单元一个变量。** 脚本读起来就是查询的语义结构。
- **注释解释编排理由，不解释算子。** 算子语义在 [05](05-operators.md) 里，
  这里只说「为什么这么排」。
- **`q.emit` 分开传结果与上下文。** `answer` 是要给用户的，`context` 是
  支撑它的完整片段——两者都要落盘，但呈现方式不同。
- **头部记录索引版本。** 同一段脚本在不同索引上结果不同，不记就没法复现。

## 执行

`Query` 对象承担三件事：注册单元、记录执行轨迹、收敛产物。
算子本身是纯函数，不持有状态——状态在 `Query` 和数据里。

```
脚本 ── 逐行执行 ──► 每个算子
                        │
                        ├─ 读索引 / 图库（IO 在这里发生）
                        ├─ 追加证据
                        └─ 返回新的 Frag
```

**IO 边界**：算子内部会读倒排索引、codegraph、embedding 产物。按
[ARCHITECTURE.md](../../ARCHITECTURE.md) 的规则，这些资源应当在
`Query` 构造时注入，而不是算子里现开——否则算子没法在内存数据上测试。

```python
q = Query("...", index=index, graph=graph_store, judge=judge_client)
```

## 编译回路：编译不必是一次性的

初稿默认「SemCon → 脚本」一步到位。不受限地看，编译更该是个**带反馈的回路**：

```
   拟一版脚本
        │
        ▼
   试跑（可以只跑便宜的算子，跳过 intent）
        │
        ▼
   看结果规模与形态
        │
   ┌────┴────────────────────────────┐
   │ 太少（0～3 个）                  │ 太多（几百个）
   │  → 放宽：& 改 |、len 放大、        │  → 收紧：加 unit、缩 len、
   │    降低 satisfier 权重门槛         │    提高权重门槛、加 avoid
   └────┬────────────────────────────┘
        ▼
   收敛后再跑 intent，出结果
```

为什么值得做成回路：**编排的好坏在跑之前判断不了**。
`io & disk` 会剩几个候选，取决于这个项目的命名习惯——
同一段脚本在 Spring 项目和内核代码上表现可能差一个数量级。

试跑时**跳过 `intent`** 是关键：它最贵，而规模判断不需要它。
便宜算子跑一遍通常在毫秒级，可以反复试。

这也回答了[08](08-open-questions.md) 里 Q2（单元之间默认什么关系）的一半——
不必一开始就猜对，试跑会告诉你。

## 优化

编译期决定顺序，执行期做局部优化。**编译期的顺序更重要**——
算子代价差好几个数量级，排错了差百倍。

### 编排原则（编译期）

1. **便宜的先跑。** `unit` / `of_kind` / `degree` 是索引查询，
   `hop` 是图遍历，`similar` 要算向量，`intent` 要调 LLM。
2. **选择性高的先跑。** 能把候选压到几十个的条件，比只能压到几百个的先跑。
3. **`intent` 永远最后。** 如果它前面还有没用上的便宜约束，是编排错了。

### 执行期优化

- **短路**：集合空了就不再往下算。
- **缓存**：同一个 `unit` 在脚本里被引用多次（`io & disk` 与后面的
  `hop(..., io)`）只求值一次。按 `(算子, 参数)` 做 key。
- **路径截断**：`hop` 的 `max_paths` 到顶就停，并 `log` 出来。
  **不能静默截断**——那会让人以为「结果就这么多」。
- **`intent` 批量**：一次判定多个候选，减少往返。

### 一个反直觉的点

「先词法后图」不总是对的。`io performance on disk` 里三个单元的词都很泛，
词法匹配后可能还剩几百个候选；而图遍历在稀疏调用图上非常快。
先用图圈定范围、再在范围内匹配，可能整体更省。

**所以顺序应该由编译期根据查询特征决定，而不是写死。**
这正是固定管线做不到的事（[01](01-motivation.md) 问题 1）。

## 安全

脚本是 LLM 生成的可执行代码，这是新设计引入的**新风险**，当前 JSON 方案没有。

初稿倾向的做法（未定，见 [08](08-open-questions.md)）：

1. **受限命名空间**：`exec` 时只注入 `codesense.ql` 的算子，
   不给 `open` / `__import__` / `os`。
2. **AST 白名单校验**：执行前解析脚本，只允许调用白名单里的算子、
   赋值、集合运算；出现 `import`、属性访问链、循环就拒绝。
3. **人工确认**：脚本对用户可见，敏感场景下先给人看再跑。

第 2 条最实在——QL 脚本的语法本来就该很窄，宽了反而说明编排出了问题。
反过来也是个好信号：**如果生成的脚本需要循环和条件分支才能表达，
说明缺算子。**

## 产物

每次查询落一个目录，和当前 `output/<project>/query_<id>/` 的组织一致：

```
query_<id>/
├── query.ql.py             编译出来的脚本（复现的唯一依据）
├── compile_trace.json      编译回路：拟了几版、每版为什么被改
├── units.json              单元与派生信号，含来源、权重、理由
├── answer.json             最终片段（节点 + 边）
├── evidence.json           每个节点的证据链
├── paths.json              路径见证
└── run_trace.json          每个算子的输入输出规模与耗时
```

两个 trace 分别回答不同的问题：`compile_trace` 回答「为什么是这段脚本」，
`run_trace` 回答「时间花在哪、哪一步把结果砍没了」。后者尤其重要——
查询返回空结果时，第一个要问的就是「哪个算子清零的」。

## 实现现状与一个负面结果

编译器已实现（`codesense/ql/compile/`），但**产出的不是 Python 脚本，是执行计划**。
理由：脚本形态的好处（可读、可改、可单步跑）在 `Plan.explain()` 里同样拿得到，
而执行 LLM 生成的代码这个代价省掉了。脚本形态留待需要时再加。

### 规划器：顺序由预估代价决定

关键是**执行前就能估选择性**——倒排索引里每个 term 都带 `df`，
所以一个单元会命中多少符号，查表就能算。实测（netty，42221 符号）：

```
执行计划：
  · 先跑最窄的 'zerocopy'（预计 310 个，占 1%，权重 ×0.99）
  · 并入 'io'（预计 12691 个，占 30%，权重 ×0.70）
  · 图约束反向：从 'zerocopy'（310 个）出发而不是 'io'（12691 个）
  · intent 放最后：它是唯一调 LLM 的算子

  步骤                          预估    实际    耗时
  unit(zerocopy)  ← 种子        310     298     2ms
  unit(io)                    12691    ...   182ms
  boost(zerocopy ↔ io)        18689   2022   103ms
  narrow(top 60)                 60      60    19ms
```

估计与实际同量级，足以支撑排序决策。

### 分工：模型做 NLP，统计做优化

这是走了弯路之后才定下来的。最初让模型一次性给出整份规格——
单元怎么分、偏好什么种类、要不要图约束，全由它定。**结果 R@100 从 65% 掉到 21%。**

根因是模型在做**它没有依据做的决定**。它不知道 `buffer` 在 netty 里命中
2365 个符号，不知道这条查询的答案是 field 不是 method——这些信息在索引里
（`df`、posting 分布），不在模型脑子里。

所以按 MySQL 优化器的思路重新划线：**优化器不问用户怎么 join，它查统计信息。**

| | 谁做 | 为什么 |
|---|---|---|
| 读懂查询、挑相关词、打分、写判定标准 | **LLM，一次调用** | 这是 NLP，模型擅长 |
| 分几个单元 | **统计** | 判据是这些词是否落在同一批符号上 → posting 重叠度 |
| 偏好什么种类 / 查哪些域 | **统计** | 看这些词的 posting 落在什么种类、什么域上 |
| 执行顺序、代价 | **统计** | `df` 让选择性在执行前就能估 |

单元划分用 posting 的 Jaccard 连通分量，而且**默认不拆**——
只有聚类真的分出结构才拆。实测 netty 零拷贝查询的词两两 Jaccard 平均
只有 0.011，统计的结论是「本来就该是一个单元」，
而这正好是表现最好的那个配置。

### 端到端的实际效果


在语义检索 benchmark 上（三次采样，R@100）：

| | grounded（手工单单元） | graph（+图重排） | planned（全流程） |
|---|---|---|---|
| 一次性给整份规格 | 54% | 65% | **21%** |
| 改成「模型做 NLP，统计定结构」 | 54% | 59% | **47%** |

从 21% 到 47%，靠的是把四类决定从模型手里拿回来。四个原因，都已修：

1. ~~单元之间取交集~~ → 改成并集。01 章早就说过「同时含有 performance 和
   disk 关键词的元素几乎不存在」，我却让规划器求交，实测把 gold 杀光
2. ~~`kind` 硬过滤~~ → 改成偏好。模型说 `class` 时心里含接口，
   而索引里 `interface` 是独立 kind——`FileRegion` 因此被静默删掉
3. ~~规格编译没缓存~~ → 补上。LLM 方差和效应同量级，不固定住就是读噪音
4. ~~单元分解摊薄信号~~ → 改成**按 posting 重叠度决定拆不拆**，
   默认不拆。模型按语义拆出的单元，其成员并不落在同一批符号上，
   等权相加就把答案摊薄了；统计能看出这一点，模型看不出。

5. ~~`USELESS_RATIO=0.5` 丢掉宽单元~~ → 提到 0.9。在 142 个符号的 petclinic 上，
   10 个词的并集轻易过半，规划器把**唯一含答案的单元**丢了。
   这和当初 ICF 下限犯的是同一个错：**把调用方明确要的东西排除，而不是降权**。

### 还差的 12 个百分点

`planned` 47% vs `graph` 59%。差距的主要来源是**全流程没有用图**——
图约束现在没人生成了（从模型手里拿掉之后，还没有对应的统计推断补上）。
`graph` 那条路是手工加的图重排，正好补上了这一块。

下一步该做的是**从统计推断图约束**：如果两个单元的 posting 之间
存在密集的调用/包含边，那它们之间就该有图约束——这同样是个统计问题，
不必问模型。

### 这对 08 章 Q2 的回答

「单元之间默认什么关系」现在有了答案，而且是三段的：

1. **并集，不是交集。** 单元本来就落在不同元素上（01 章）。
2. **拆不拆由统计定，不由语义定。** 判据是词是否落在同一批符号上。
3. **拆错比不拆贵。** 所以门槛要偏保守——宁可一个宽单元，
   不要几个把答案摊薄的窄单元。
