# 09 落地到具体项目：分词、嵌入与扩展索引

LLM 能给出靠谱的通用词表——`performance` → `buffer`、`async`、`cache`。
但项目里可能写的是 `buf`，注解可能是自定义的 `@AppCache` 而不是 `@Cacheable`。

**通用知识和项目实际写法之间隔着一层，这一章讲怎么架桥。**

---

## 先看一个决定方案的事实

在样例项目（youlai-boot，1718 个符号）上实测：

| 项目里的写法 | 出现次数 | 完整形式 | 出现次数 |
|---|---|---|---|
| `dept` | 9 | `department` | **0** |
| `dict` | 6 | `dictionary` | **0** |
| `config` | 4 | `configuration` | **0** |
| `auth` | 2 | `authentication` | 16 |
| `msg` | 12 | `message` | 8 |

**前三行否掉了一个直觉方案。**

「在项目语料上训一个 token embedding，然后查 `department` 的近邻找到 `dept`」——
做不到。`department` 在项目里出现 **0 次**，任何在项目语料上训的模型
词表里根本没有这个词，无从算相似度。

而这恰恰是最需要解决的情况：**项目只用缩写，从不写全称。**
`auth`/`msg` 那种两种写法都有的反而好办。

### 语料规模也不支持从头训

| 量 | 实测 |
|---|---|
| 增强调用链语料 | 154,686 条 / **103 万 token** |
| 项目词表 | 313 个 term |
| 符号名切出的单元 | 464 个不同单元 / 3,884 次出现 |

103 万 token 对 word2vec 来说偏小（通常要 10⁷ 以上），但更要命的是
**词表只有几百**——在这种规模上学 100 维向量必然过拟合。

更根本的问题是**信号不对**：调用链上的分布式相似度给的是**话题相关**
（`user` 挨着 `role` 挨着 `dept`），不是**同义**。而我们要的是同义。

### 所以方案是「锚定」，不是「训练」

> **不要建一个项目自己的向量空间，要把项目的表层写法锚进通用向量空间。**

通用模型已经知道 `buffer ≈ cache`、`disk ≈ storage`。项目语料的价值不在于
重新学这些语义，而在于告诉你**这个项目用哪些表层形式来指代它们**。
后者是个低数据量问题。

---

## 一、统一分词

### 现在的问题

当前用 sentencepiece BPE。BPE 的目标是**最小化编码长度**，不是找语素。
后果是切分边界和词形无关：`buf` 可能切成 `bu|f`，而 `buffer` 整体成词，
两者一个共享单元都没有——查询侧和代码侧对不上。

### 建议：词典驱动的 Viterbi 切分

把切分变成**在一个词典上求最优路径**，而不是学一套合并规则。

词典由三部分构成：

1. **英文词表**（带词频）
2. **项目自己的 camel/下划线切分单元**（带项目内词频）
3. **通用缩写表**（`mgr`、`cfg`、`idx`……）

对一段全小写、无边界的标识符（`bufmgr`、`readahead`），
用 Viterbi 求使 `Σ log P(unit)` 最大的切分。

**为什么比 BPE 好**：

- 边界落在语素上：`readahead` → `read|ahead`，不会切成 `rea|dahead`
- 项目特有单元是一等公民
- 确定性、可解释——能说清为什么在这切

### camelCase 是免费的监督信号

这是最容易被忽略的一点：**作者写 `bufMgr` 时，已经告诉了你 `buf` 和 `mgr`
是这个项目里的原子单元。**

实测样例项目：1718 个符号切出 **464 个不同单元，3884 次出现**；
其中长度 ≤4、出现 ≥3 次的有 **84 个**——那批就是本项目的缩写候选。

所以词典的第 2 部分不用人工整理，扫一遍符号表就有了，而且带频次。

### 同一个切分器用于两端

```
查询  "io performance on disk"  ──切分──►  [io, performance, disk]
标识符 bufMgr / readahead       ──切分──►  [buf, mgr] / [read, ahead]
```

**必须是同一个切分器、同一份词典。** 这是「统一」的全部含义——
两端落进同一个符号空间，后面的扩展才有意义。

### 切分之后还有一层：规范化

```
表层形式        规范形
buf, bfr   →    buffer
mgr        →    manager
dept       →    department
```

**索引应当以规范形为键**，而表层→规范形的映射就是项目特有知识的落脚点。
这层映射怎么得到，是下一节。

---

## 二、表层形式 → 规范形：三步

不训练项目向量空间，改成三步流水线。全部离线，一次性。

### 第 1 步：正字法候选生成

对每个项目单元 `t`（如 `dept`），从候选全称集合中找正字法上兼容的：

| 模式 | 例 | 强度 |
|---|---|---|
| 前缀 | `buf` ⊂ `buffer` | 强 |
| 辅音骨架 | `mgr` vs `manager`（m,g,r） | 强 |
| 子序列 | `bfr` ⊂ `buffer` | 中 |
| 首字母缩合 | `dto` ← `data transfer object` | 中 |

候选全称从两处来：英文词表，以及**编译期 LLM 为各单元派生的词**
（[04](04-query-unit.md)）——后者更重要，因为它直接对准了当前查询关心的概念。

现有的 `AbbreviationGenerator` 已经实现了前三种模式，但用法是**反的**：
它现在从查询词生成候选缩写再去语料里碰。这里要**倒过来用**：
拿项目里真实存在的单元，去和候选全称配对打分。

倒过来的好处：候选空间从「所有可能的缩写」（`abbreviate("readahead")`
会生成 46 个）缩小到「项目里真实出现的 464 个单元」，
而且不会漏掉生成规则覆盖不到的怪写法。

### 第 2 步：上下文打分（关键的一步）

正字法会给出歧义候选：`buf` 兼容 `buffer`，也兼容 `buffalo`。用上下文消歧。

**不要为此训练项目向量。** 改用这个技巧：

```
对项目单元 t：
    ctx(t) = 与 t 在同一标识符 / 同一调用链中共现的单元
    v(t)   = Σ  icf(u) · general_embed(u)   /  Σ icf(u)
             u∈ctx(t)
```

即：**用通用模型嵌入 t 的上下文，把 t 定位到通用向量空间里**。
然后

```
score_ctx(t, w) = cos( v(t), general_embed(w) )
```

为什么这样可行：

- **不估计任何参数**，只是对预训练向量做加权平均——所以 103 万 token
  的小语料够用，甚至几千 token 也能给出有意义的信号
- `department` 不在项目里也没关系：它有**通用**向量，
  而 `dept` 通过上下文（`user`、`role`、`tree`、`list`）拿到了通用空间里的坐标
- ICF 加权直接复用现有实现，压掉 `get`/`by`/`id` 这类无信息词
  （实测 `get` 出现 207 次，不压会主导所有上下文向量）

这一步用的是**已有的两个通道**：ICF（`icf_term_embedding.py`）
和通用语义模型（`semantic_term_embedding.py`）。差别在于组合方式——
现在是拿它们直接比两个词，这里是拿它们给项目单元求一个通用空间里的坐标。

### 第 3 步：LLM 复核

经过前两步，候选对通常只剩几百个。全部交给 LLM 逐个确认：

```
项目里有个标识符片段 `dept`，它出现在这些符号里：
  DeptController, DeptService, listDeptTree, getDeptById, SysDept
问：`dept` 是不是 `department` 的缩写？
```

给上下文而不只给两个词——这让判断可靠得多。几百次调用、一次性、离线，
成本可忽略，而准确率远高于任何自动打分。

**产物是一份项目专属的缩写词典**，可读、可人工审、可进版本库：

```json
{
  "dept": [{"canonical": "department", "score": 0.94,
            "evidence": {"ortho": "prefix", "ctx": 0.81, "llm": "yes"},
            "seen_in": ["DeptController", "listDeptTree"]}],
  "dict": [{"canonical": "dictionary", "score": 0.91, ...}]
}
```

**可审是重点**。这份表决定了整个检索的召回边界，出问题时要能一眼看出
是哪个映射错了——比调一个端到端的相似度阈值容易得多。

## 三、带相似度阈值的索引

你提的方向对，但**实现上不该把索引本身变模糊**。

### 建议：预计算扩展表，索引保持精确

```
扩展表:  规范形 → [(项目表层形式, 分数, 理由)]

buffer → [(buf, 0.91, "prefix+ctx"), (bfr, 0.72, "subseq")]
```

查询时：

```
单元给出规范词 buffer
   → 查扩展表得到 [buf, bfr]
   → 对每个做**精确**倒排查询
   → 命中分数 = 单元权重 × 扩展分数
```

比「让索引支持相似度」好在四点：

1. **索引保持精确**，不需要改数据结构，也不引入 ANN 的近似误差
2. **可解释**：能直接告诉用户「命中 `buf`，因为它与你的查询词 `buffer`
   相似度 0.91」
3. **可审计**：扩展表是张表，能 dump 出来给人看
4. **调阈值不用重建索引**

代价是扩展表要离线算。但词表只有几百量级，全量 |V|² 也就几十万次比较，
秒级完成。即便到 10 万词，用 ANN 建表也不是问题。

### 阈值应该按词自适应，不能全局一刀切

这一点很关键。用 ICF 调：

```
threshold(t) = base + k · (1 − norm_icf(t))
```

- **高 ICF 的稀有词**（`swap`、`sector`）：阈值放低，多扩几个。
  它们本身有区分度，扩错了也不至于淹没结果。
- **低 ICF 的泛词**（`get`、`data`、`by`）：阈值拉到极高，**基本不扩**。
  实测 `get` 出现 207 次——什么都和它「相似」，扩展只会制造噪音。

一个更省事的等价做法：**低 ICF 的词直接不进扩展表**。

## 四、注解走同一套

`@Cacheable` vs 项目自定义的 `@AppCache`——注解名本身就是标识符，
所以完全复用上面的机制：

```
@AppCache  ──切分──►  [app, cache]  ──规范化──►  [application, cache]
```

于是 `annotation` satisfier 不该是对字面名字的正则，而是
**对切分后的注解名做单元式匹配**。这样 `@AppCache`、`@CacheAside`、
`@Cacheable` 会一起命中 `cache` 这个规范形，分数按扩展分数区分。

注解另有一个几乎免费的结构信号：**共同标注在同一批方法上的注解是相关的**。
样例项目规模小，这个信号弱，但在大型 Spring 项目里很可用。

## 五、怎么知道这套有没有用

**别一上来就看端到端指标**——那里面混了太多变量。
针对这一层单独建一个小 gold set：

- 人工标 50–100 对 `(项目表层形式, 规范形)`。从上面那 84 个短单元起手，
  半小时能标完。
- 指标就是扩展表相对这份标注的**精确率与召回率**。

这比端到端评测便宜一个数量级，而且直接对准这个组件。
调阈值、调融合权重都该看这个数，不是看最终检索结果。

**这份 gold set 还有个副作用**：它顺带回答了
[08](08-open-questions.md) 里 Q4a/Q4b（权重怎么定）——
至少在这一层，权重从此有据可调而不是拍脑袋。

---

## 小结：四个判断

1. **不要在项目语料上从头训 embedding。** 词表几百、语料百万级 token，
   而且要找的全称（`department`）在项目里出现 0 次——训不出来。

2. **要把项目表层形式锚进通用向量空间。** 靠上下文的 ICF 加权平均，
   不估计参数，小语料也成立。

3. **切分要词典驱动而非 BPE**，词典的项目部分从 camelCase 边界免费获得，
   而且查询侧和代码侧必须共用同一个切分器。

4. **索引保持精确，模糊性放进预计算的扩展表。** 可解释、可审计、
   阈值按 ICF 自适应。

依赖关系：**分词决定词表，词表决定扩展表，扩展表决定召回上限。**
所以三者要一起设计，不能分开做。
